# `@spatialdata/layers`

The **deck.gl–native** package for composable spatial rendering: a canonical
ordered **`RenderStack`** contract, a top-level **`SpatialLayer`**
`CompositeLayer`, and versioned, JSON-serializable **`SpatialLayerProps`**.

## Role

- **`SpatialLayer`** — validates props and renders `shapes` sublayers. Images,
  labels and points are composed by `@spatialdata/vis` from the layers below.
- **`RenderStack`** — ordered saved/render state for SpatialData entries, host
  overlay descriptors, and the groups that hold them. This replaces public
  dependence on parallel `layers` maps plus `layerOrder` arrays.
- **`IsolatedGroupLayer`** — draws a group's members into their own target and
  composites it with an opacity and blend mode.
- **`spatialLayerPropsSchema`** / **`migrateSpatialLayerProps`** — runtime validation and migrations for saved views, URL state, and integrators (e.g. MDV chart config).
- **Renderers** — `createShapesDeckLayer`, `LabelsLayer`, and `PointsLayer`
  with its `PointsDataEngine`.

## Relationships

| Package | Responsibility |
|--------|-----------------|
| `@spatialdata/core` | SpatialData on Zarr: elements, transforms, read APIs, the Resource Resolver |
| `@spatialdata/avivatorish` | OME loaders, tile cache, channel stats, Zustand image state |
| `@spatialdata/layers` | Canonical render-stack schema and deck renderers for shapes, labels and points |
| `@spatialdata/vis` | **SpatialCanvas** React/Viv adapter: render stack ↔ resources ↔ viewport |

## API tiers

See also the [visualization overview](../vis/overview): deck-only integrators can use **`@spatialdata/layers`** without React; headless loader usage is **`@spatialdata/avivatorish`**; full UI is **`@spatialdata/vis`**.

## Shapes, labels and points

Shapes rendering lives in this package rather than in `@spatialdata/vis`:

- polygon fallback for JS/WKB payloads and a columnar branch for `geoarrow-table` runtime data
- row alignment, picking, and tooltip resolution are driven by stable feature identity plus shared row-index metadata
- `buildShapeFillColorByFeatureId()` turns a table column plus already-resolved
  `rowIndexByFeatureIndex` into per-feature colour maps; it deliberately does
  not resolve SpatialData table associations itself
- the public shapes config is representation-agnostic, so the backend can change
  without changing saved props. `@geoarrow/deck.gl-geoarrow` cannot do dynamic
  per-feature hide/fade, so shapes stay on our own binary layer over a GeoArrow data plane

For shapes, the contract is stable feature identity plus table-join-driven styling/filtering. `@spatialdata/core` loads render-oriented shape data, `@spatialdata/layers` turns that into deck layers, and `@spatialdata/vis` consumes the shared behavior for viewer use.

**Labels** now follow that same contract. The colour-encoding core is shared
rather than duplicated per kind:

- `featureColorEncoding` holds what is common — the `auto`/`categorical`/
  `continuous` mode decision, `resolveCategoricalPalette()`, numeric ramps, and
  the missing-value policy — plus `FeatureColorBuffer`, the precomputed-RGBA
  currency both kinds render from.
- `shapeColorEncoding` and `labelColorEncoding` are the thin per-kind surfaces:
  `buildShapeFillColorByFeatureId()` and `buildLabelFillColorByFeatureId()`.
- Shapes index colour by feature index; labels have no geometry, so
  `buildLabelColorLut()` produces a lookup table indexed by the label's own
  integer instance id that the bitmask fragment shader samples. Either way a
  feature-state change re-uploads only the small table, never the tiles.

The default categorical palette is `DEFAULT_FEATURE_CATEGORICAL_PALETTE`
(`'oklab'`), whose colour is a pure function of the category index and therefore
cannot repeat — see the
[behaviour-change note](../vis/headless-viewer#choosing-the-colour-scheme).

**Points** follow the same split. `@spatialdata/core` loads and tiles the data
([Loading points and shapes](../core/points-and-shapes)) and its `PointsResolver`
owns the cache and lifecycle. `PointsDataEngine` and `PointsLayer` here own the
deck-facing renderer: feature filtering and colour-by-feature, resident and
viewport-tiled render strategies, and picking. Per-layer runtime state such as
the hovered feature rides the engine rather than the saved config.

## Render stack contract

The public saved/render order is `renderStack.entries`, not a separate
`layerOrder` array:

```ts
import type { RenderStack } from '@spatialdata/layers';

const renderStack: RenderStack = {
  schemaVersion: 2,
  entries: [
    {
      kind: 'spatial',
      id: 'image-morphology',
      source: { elementType: 'image', elementKey: 'morphology_focus' },
      props: { opacity: 0.8 },
    },
    {
      kind: 'group',
      id: 'points',
      props: { blendMode: 'screen', opacity: 0.5 },
      children: [
        { kind: 'host', id: 'deck:scatter', source: { hostLayerId: 'deck:scatter' } },
      ],
    },
  ],
};
```

`source` holds structural identity. `props` holds renderer inputs. The
[Resource Resolver](../core/resource-resolver) and deck/Viv `updateTriggers` decide what actually invalidates IO,
geometry, attributes, or tile data; do not add a second visual-vs-structural
prop registry.

### Groups

The stack is a tree. A `group` entry holds its children as entries, drawn in
order, bottom to top, and entry ids are unique across the whole tree. Code that
reads `stack.entries` sees only the top level: use `walkRenderStackEntries` to
visit every entry, or `findRenderStackEntry` to look one up by id.

A group's props are typed, and all optional:

| Prop | Default | Meaning |
|------|---------|---------|
| `opacity` | `1` | The group's opacity, from 0 to 1 |
| `blendMode` | `'pass-through'` | `pass-through`, `normal`, `additive`, `multiply`, `screen`, `max` or `min` |
| `isolate` | `false` | Draw the children into their own target before compositing |

`resolveRenderStackGroupProps(group)` applies the defaults. The two ways a group
draws differ where its children overlap:

- **Pass-through** (the default) adds no layer. The group's visibility and opacity
  multiply into each child's, so at 50% two overlapping children each draw at 50%
  and their overlap comes out darker than either. It costs nothing.
- **Isolated** (`isolate: true`, or any blend mode but `pass-through`) draws the
  children into a target of their own, then composites that once with the group's
  opacity and blend mode, so the overlap matches the rest of the group. It costs
  one viewport-sized target per group and view.

Leaf entries also accept `props.blendMode`. It is saved, but not drawn yet:
blending goes through groups.

`renderStackToDeckLayers` in `@spatialdata/vis` turns a stack into deck layers,
with an `IsolatedGroupLayer` for each isolated group. It needs no SpatialData or
Viv, so a host with only its own layers can use groups too. `IsolatedGroupLayer`
draws its members under ids scoped to the group (`<group>/<member>`), so a layer
moving into or out of a group never keeps deck state from its old place. A pick
through a group names the member's layer; `getIsolatedGroupMemberId(info)` gives
its own, unscoped id.

### Saved v1 stacks

v1 stacks were flat, with each group naming other top-level entries by id.
`renderStackSchema` upgrades them on parse. `migrateRenderStack` does the same as
a plain function, for hosts that keep the stack as live state, and returns notices
for child ids it had to drop: ids that name no entry, or that an earlier group
already took. A saved stack never fails to load for that reason. See
[ADR 0007](https://github.com/Taylor-CCB-Group/SpatialData.js/blob/main/docs/adr/0007-render-stack-groups.md)
for the decisions behind groups.

## React-agnostic usage

`@spatialdata/layers` has no React dependency. A minimal deck-only path:

```ts
import {
  buildShapesPrebuiltData,
  createShapesDeckLayer,
  buildShapeFillColorByFeatureId,
} from '@spatialdata/layers';
import {
  createFeatureTableAlignment,
  loadFeatureRowIndexByFeatureIndex,
} from '@spatialdata/core';

// After loading renderData + table column from core:
const fillColorByFeatureId = buildShapeFillColorByFeatureId({
  featureIds: renderData.featureIds,
  rowIndexByFeatureIndex: alignment.rowIndexByFeatureIndex,
  column: obsColumn,
  mode: 'categorical',
  alpha: 200,
});

const layer = createShapesDeckLayer(
  renderData,
  {
    kind: 'shapes',
    elementKey: 'cell_shapes',
    visible: true,
    featureState: { fillColorByFeatureId },
  },
  { id: 'shapes', prebuilt: buildShapesPrebuiltData(renderData) }
);
```

For Viv images and async SpatialData layer orchestration without the
`SpatialCanvas` UI, use `@spatialdata/vis` headless APIs
([Headless viewer guide](../vis/headless-viewer)) or compose
`createShapesDeckLayer` output with your own `Deck` / `DeckGL` stack.
